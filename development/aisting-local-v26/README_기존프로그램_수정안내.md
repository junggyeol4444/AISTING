기존 `OriginalPlanStudio` 방송인 홈에 **“공식 WebSocket 초기화 확인 (대화·음성 요청 안 함)”** 버튼을 추가했습니다. 사용자에게 매 연결 승인을 요청한 뒤, 이미 실행 중인 로컬 공식 서버의 `ws://127.0.0.1:12393/client-ws`에만 연결합니다. 공식 소스의 `set-model-and-conf` 초기화 메시지를 확인하고 실제 서버가 전달한 설정 이름과 Live2D 모델 이름/경로를 표시합니다. `text-input`, `mic-audio-data`, `ai-speak-signal`, TTS 합성·음성 재생·OBS 송출 요청은 보내지 않습니다. 서버 연결만으로도 세션/로그가 생성될 수 있으므로 버튼 클릭 전 설명과 승인 절차가 있습니다.

이는 기존 v7의 HTTP 200 확인보다 구체적인 **공식 WebSocket 초기화 프로토콜 진단**이며, 서버 바이너리의 진위 보증, 실제 LLM 응답, 실제 GPT-SoVITS 한국어 음성, Live2D 아바타 렌더링·립싱크 성공 판정은 아닙니다. 검증된 원본 공식 코드 경로: `src/open_llm_vtuber/routes.py`, `src/open_llm_vtuber/websocket_handler.py`, `src/open_llm_vtuber/live2d_model.py` (GitHub READ ONLY 조회).

`original_plan_ws.py` 모듈을 기존 소스 **사본**에만 추가하도록 패치 적용 스크립트를 변경했습니다. 빌드 스크립트도 검증된 로컬 사본 출처 기록과 v8 모듈을 요구하고, 새 타임스탬프 출력 폴더를 사용하도록 수정해 원본 체크아웃/이전 EXE를 보호합니다. 이 Windows 빌드 스크립트는 이 Linux 환경에서 실행되지 않았습니다.

검증: Python 보조 단위검사 **50개 통과**(v7 40개 + v8 10개), Linux/Xvfb Tk 실제 UI 표시 검사 통과. WebSocket 단위검사는 프로토콜 파서/권한 차단만 확인했고 **실제 공식 서버 접속은 실행하지 않았습니다**. 기존 전체 AISTING 원본을 확보하지 못했으므로 실제 전체 소스에 패치 적용·회귀 검사와 Windows EXE 빌드도 미완료입니다.

## v9 후속 변경 — GitHub READ ONLY 고정 커밋 원본 확보 도구

이전 실행 환경에서는 GitHub DNS 문제로 전체 기존 소스의 **실제 로컬 복원**을 수행하지 못했습니다. 이를 해결하기 위한 **원본 보존 도구** `fetch_existing_main_snapshot_readonly.py`를 추가했습니다. 도구 자체를 작성·검사한 것이며, 이 회차에 실제 GitHub 전체 소스를 받은 것은 아닙니다. 원본의 공식 커밋 `2269205998201165e024a22d0adef576e6cac0c6`과 기존 `desktop.py` blob SHA가 일치해야만 새 로컬 소스 스냅샷을 남깁니다. 공개 GitHub 소스만 읽고, GitHub에 쓰지 않습니다.

```powershell
# 기본은 안내만 표시 (네트워크 접속·파일 생성 없음)
python fetch_existing_main_snapshot_readonly.py --destination "D:\AISTING_main_readonly_snapshot"
# 원본 확보를 명시적으로 허용한 환경에서만, 새 경로에 GitHub 공개 원본 소스 복사
python fetch_existing_main_snapshot_readonly.py --destination "D:\AISTING_main_readonly_snapshot" --fetch
# 원본 스냅샷은 보존하고, 별도의 개발 사본만 준비
python prepare_local_source_copy.py --source "D:\AISTING_main_readonly_snapshot" --destination "D:\AISTING_local_copy" --copy
# 실제 패치 전에 검토하고, 별도 승인 후 사본에만 적용
python apply_to_existing_aisting.py --source "D:\AISTING_local_copy"
python apply_to_existing_aisting.py --source "D:\AISTING_local_copy" --apply
```

**주의:** `--fetch`는 프로그램 **소스 코드**를 공개 GitHub에서 내려받는 동작입니다. 사용자 승인이 없는 프로그램·모델·플러그인 설치나 다운로드를 허가하는 뜻이 아닙니다. 사용자가 기존 AISTING 원본 전체 소스를 이미 보유했다면 네트워크 확보 대신 그 원본으로 기존 `prepare_local_source_copy.py` 절차를 사용하세요. ZIP 경로·파일·원본 SHA 불일치 시 실패하고 새 소스 폴더를 폐기하며, 기존 파일은 덮어쓰지 않습니다. `RELEASE_NOTES_v9.md`에 정확한 변경점과 미검증 사항이 있습니다.

현재 v9 보조 검사 60개 통과. Windows EXE는 빌드하지 않았고, v9 빌드 스크립트의 새 출력 폴더는 `dist-local-revision-v9-<실행시각>`입니다.

## v10 후속 변경 — 실제 GPT-SoVITS 참조 음성 파일과 로컬 API 주소 확인

기존 2단계 GPT-SoVITS 창에서 사용자가 이미 소유한 WAV/FLAC을 선택하면 이제 **실제 WAV/FLAC 컨테이너 헤더**를 읽기 전용으로 확인합니다. 확장자만 WAV인 가짜 파일은 설정에 기록하지 않습니다. 검사는 오디오 재생·학습·모델 합성·화자 권리 확인을 수행하지 않습니다. 공식 로컬 GPT-SoVITS API 주소(`http://127.0.0.1:9880/tts` 기본값)는 사용자가 창에서 선택·변경할 수 있고, 변경 전 확인 창에 명시됩니다. 외부/유료 API는 사용자 결정 없이 자동 지정하거나 연결하지 않습니다. 설정 저장만으로 실제 한국어 음성이 작동했다고 판정하지 않습니다.

v10 보조 검사 **63개 통과**, Linux Tk 화면 표시 검사 통과. 기존 전체 AISTING 원본 소스 사본에 적용, Windows EXE 빌드, 실제 한국어 음성·Live2D·OBS 기능 검증은 **미완료**입니다. 세부 내용은 `RELEASE_NOTES_v10.md`를 참조하세요.


## v11 후속 변경 — 공식 설정의 무손실 백업·교체 보강

이번 회차는 기존 v10 수정 패키지를 복원하여 **공식 Open-LLM-VTuber `conf.yaml`을 변경하는 기존 두 기능**(저장된 캐릭터 적용, GPT-SoVITS 설정 적용)의 파일 보존 동작을 수정했습니다. `original_plan_config_io.py`를 기존 패키지에 추가하고, 기존 두 모듈이 이 공통 로컬 설정 저장 절차를 사용하도록 연결했습니다.

- 원본이 UTF-8 BOM과 Windows CRLF 줄바꿈을 사용하면 수정 후에도 보존합니다.
- 사용자 승인 후 설정을 바꾸기 전에 고유한 개인용 `.bak`를 생성하고 `fsync` 후 원본 바이트와 일치하는지 검사합니다. 기존 설정 파일이 읽은 이후 바뀌었거나 링크로 교체되었으면 덮어쓰지 않습니다.
- 새 설정은 같은 폴더의 임시 파일에 기록·동기화하고, 원본 권한을 유지한 채 교체합니다. 교체 실패 시 기존 설정을 보존하고 임시 파일을 제거합니다.
- 기존 설정과 변경 결과가 동일하면 백업을 새로 만들지 않습니다. Windows 빌드 스크립트는 신규 모듈 존재를 검사하며, 기존 EXE를 덮어쓰지 않는 v11 출력 폴더를 사용합니다.

**검사:** 로컬 단위·보호 검사 69개 통과, Linux Xvfb Tk 화면 검사 통과. 신규 6개 검사는 임시 폴더에서만 동작하며 실제 LLM/TTS/Live2D·OBS 기능 증거가 아닙니다. 기존 전체 AISTING 원본은 아직 이 패키지에 없으므로 전체 사본에 v11을 적용하거나 Windows EXE를 빌드하지 못했습니다.

자세한 변경 파일과 검사 한계는 `RELEASE_NOTES_v11.md`를 참조하세요.

## v13 패치 후 읽기 전용 전체 파일 보존 감사

v12는 **패치 전** 기존 파일 전체 해시를 검사했다. v13에서는 **패치 후**에도 기존 설정·기억 DB·100단계 기록·기존 소스가 그대로인지, `desktop.py`가 검증된 정확한 수정안인지, 원본 백업 및 추가 모듈이 바이트 단위로 올바른지 감사할 수 있다. 이 감사는 실제 AI/음성/아바타/방송 기능 검증이 아니다.

```powershell
# 기존 원본의 검증된 별도 사본에 패치를 적용한 다음 실행 (읽기 전용)
python audit_local_patch_preservation.py --source "D:\AISTING_local_copy"
```

이제 `build_existing_windows.ps1`도 **PyInstaller 실행 전** 위 감사를 자동 호출하며 실패하면 빌드를 중단한다. 감사 자체는 새 파일을 쓰거나 원본을 바꾸지 않는다. 자세한 사항은 `RELEASE_NOTES_v13.md` 참조.

## v14 기존 전체 원본의 빈 폴더/링크 안전 복사

v14는 기존 파일 SHA-256뿐 아니라 **빈 디렉터리를 포함한 원본 전체 디렉터리 구조**를 보존합니다. 원본 검사와 실제 복제 사이에 링크가 새로 생기는 경우에도 POSIX에서 링크를 따라가 외부 파일을 복사하지 않도록 개선했습니다. Windows는 원자적 링크 교체 차단까지 보증하지 않으므로 원본 소스가 사용 중인 상황에서 복제하지 말고 안정된 상태에서 수행하세요. 기존 v13 이하의 사본 기록은 폴더 구조 정보가 없으므로 v14 적용 전에 **원본을 보존한 채 별도의 새 사본을 다시 만들어야 합니다**. 절차와 96개 로컬 보조 검사/실제 기능 미검증 범위는 `RELEASE_NOTES_v14.md` 참조.


## v15 추가: 저장된 캐릭터와 공식 설정 파일의 읽기 전용 비교

기존 AISTING에서 전용 **캐릭터 확정 저장**으로 저장된 이름·말투·성격은 새 스튜디오 탭에서 표시됩니다. 새 버튼 **확정 캐릭터 ↔ 공식 conf.yaml 비교 (읽기 전용)**는 공식 프로그램 폴더의 기존 설정 파일과 확정된 캐릭터 문구를 비교하지만, 미저장 편집 초안을 읽거나 적용하지 않으며 파일을 수정하지 않습니다. 불일치 시 명시적 승인 없이 공식 설정을 변경하지 않습니다. 일치해도 실제 실행 중인 LLM에 적용되었거나 음성/아바타가 작동한다는 증거는 아닙니다.

## v16 추가 — 전용 캐릭터 확정 저장 시 최신 방송 설정 보존

기존 `desktop.py`의 전용 **캐릭터 확정·저장** 버튼이 이제 `original_plan_persona_store.commit_character_identity`를 호출하도록 로컬 패치를 보완했습니다. 다른 창/프로세스가 최근 저장한 **유효한 비캐릭터 설정**을 다시 읽고 유지하며, 기존 설정은 비공개 백업 후 변경합니다. 일반 **방송 설정 저장**만으로 캐릭터 초안이 확정되는 동작은 추가하지 않았습니다. 원본 전체 소스가 아직 없어 실제 기존 프로그램에 적용·재시작 복원을 검증하지 못했습니다. `RELEASE_NOTES_v16.md` 및 `WINDOWS_REAL_DEVICE_VALIDATION_v16.md` 참고.


## v17 — 방송 설정 저장과 캐릭터 확정 저장의 파일 수준 분리

`방송 설정 저장 (캐릭터 제외)`는 더 이상 창을 열 때의 캐릭터 필드를
설정 파일에 다시 기록하지 않습니다. `original_plan_persona_store.py`의
`save_broadcast_without_persona`가 최신 설정 파일에서 확정된 캐릭터를

바뀐 경우에는 조용히 덮어쓰지 않고 충돌 오류를 표시합니다.
`캐릭터 확정·저장`은 기존 전용 동작을 유지합니다. 두 저장 경로 모두
기존 설정을 비공개 백업한 후 교체합니다. 저장 버튼을 누르기 전에는
파일을 변경하지 않습니다. 원본 전체 소스 적용 및 Windows/실제 방송
검증은 여전히 미완료입니다. 상세 내용은 `RELEASE_NOTES_v17.md`.


## v18 — 캐릭터/방송 설정 저장의 프로세스 간 충돌 차단

전용 캐릭터 확정 저장과 일반 방송 설정 저장은 이제 동일한 OS 파일 잠금을 획득한 뒤에만 기존 설정을 읽고 변경합니다. 다른 창이 저장 중이면 기다리면서 몰래 덮어쓰지 않고 오류로 중단합니다. 잠금 파일은 안전을 위해 유지되며 삭제하지 않습니다. **이전 `offline_settings.save_settings`처럼 잠금에 협력하지 않는 쓰기 경로까지 완전 보호하지는 못합니다.**
