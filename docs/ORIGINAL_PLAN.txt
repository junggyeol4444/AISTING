================================================================
AI 방송인 프로젝트 기획안
(사람 손 안 쓰고 AI가 자율로 운영 / 사람처럼 느껴지는 AI 방송인 /
 운영자는 유지보수만)
================================================================


================================================================
1부. 프로젝트 개요와 핵심 철학
================================================================

[1-1. 한 줄 정의]
사람의 개입 없이 24시간 자율로 운영되는, "사람처럼 느껴지는" AI 버추얼
방송인. 운영자는 켜두고 유지보수만 한다.


[1-2. 가장 중요한 원칙 — "사람처럼" + 판단은 운영자가]

이 프로젝트의 성패는 "사람처럼 느껴지는가"에 달려 있다.
단, 여기서 결정적으로 중요한 두 가지 전제가 있다.

전제 1) "사람처럼"의 판단 주체는 운영자(사용자)다.
  AI나 개발자가 "이러면 사람 같겠지"라고 추측해서 행동 규칙을 미리
  못박지 않는다. 일단 자연스럽게 만들고, 운영자가 보고 이상하면
  그때 알려주고 고친다. "AI티" 같은 걸 미리 정의해서 가두지 않는다.

전제 2) 기본은 "다 반응 + 자연스러운 속도"다.
  ※ 흔한 오해: "사람 스트리머는 채팅을 다 못 읽으니까 AI도 일부만
     답하고 딜레이를 넣어야 사람 같다" → 이건 틀렸다.
  - 사람 스트리머가 채팅을 다 못 읽는 건 채팅이 쏟아져서지, 일부러
    무시하는 게 아니다. AI 방송인은 오히려 채팅을 다 읽고 다 반응해
    주는 게 더 좋은 방송이고, 시청자도 자기 채팅 읽어주는 걸 좋아한다.
  - 즉답이 필요한 순간이 당연히 있다. "ㅋㅋㅋ"에 3초 뒤 반응하면 그게
    더 어색하다. 빠르게 받아쳐야 살아있는 방송이다.
  - 따라서 인위적 딜레이나 채팅 선별을 디폴트로 박지 않는다. 자연스러운
    속도로 다 반응하는 걸 기본으로 깔고, 조정이 필요하면 운영자가 지시.

[그래서 기본 방침]
- 채팅: 기본적으로 다 읽고 다 반응. (못 따라갈 만큼 쏟아질 때의 처리는
  나중에 운영자 판단으로 추가)
- 속도: 자연스러운 속도로 응답. 인위적 딜레이를 기본으로 넣지 않음.
  맥락상 빠른 반응이 맞으면 빠르게.
- 말투/성격: 페르소나(3부)로 캐릭터를 잡되, "이렇게 말 흐려라" 같은
  행동 규칙을 미리 강제하지 않음.
- 모든 조정은 "운영자가 보고 → 이상하면 지시 → 수정" 구조로.

※ 페르소나와 행동은 운영하면서 운영자 피드백으로 다듬는다. 처음부터
   완벽하게 정의하려 하지 않는다. 운영자가 핸들을 쥔다.


[1-3. 운영자의 역할 = "유지보수만"]
완전 무인은 환상이다. 현실적으로 운영자가 손대야 하는 최소 영역:

- 서버가 죽었을 때 재시작 (자동 재시작 설정으로 최소화 가능)
- AI가 사고 쳤을 때 (이상한/부적절 발언) 페르소나·필터 수정
- 가끔 말투나 콘텐츠 방향 조정
- API 비용 관리, 토큰 갱신 등

→ 목표는 "완전 무인"이 아니라 "하루 5~10분 점검 수준"의 저관리.


[1-4. 이 기획안 전체 범위]
2부: 전체 시스템 구조
3부: 페르소나 설계 (캐릭터를 잡되, 행동은 운영자가 조정)
4부: 방송 자동화 로직 (시작/진행/종료 판단)
5부: 공지 자동화 (디스코드·카페 등)
6부: 기술 스택과 오픈소스 선택
7부: 단계별 구축 로드맵
8부: 비용·리스크·운영 현실


================================================================
2부. 전체 시스템 구조
================================================================

[2-1. 큰 그림 — "두뇌 + 손발 + 스케줄러"]
오픈소스 하나로 안 끝남. 여러 부품 조립. 사람 몸에 비유:

- 두뇌 (AI 코어): 무슨 말/반응 결정 = LLM + 페르소나
- 입 (음성): 말을 목소리로 출력 = TTS (음성 클로닝)
- 얼굴 (아바타): 화면 속 캐릭터 = Live2D / VRM
- 귀·눈 (입력): 채팅 읽기, 게임 화면 보기 = 채팅수집 + 화면인식
- 손발 (행동): 방송 on/off, 게임 조작, 공지 = OBS제어 + 조작 + 공지봇
- 심장박동 (스케줄러): 정해진 시간에 작동 = 자동화 컨트롤러

→ 두뇌·입·얼굴·귀까지는 기존 오픈소스가 거의 해줌.
  새로 만들 건 주로 손발과 심장박동(스케줄러/종료판단/공지).


[2-2. 하루 동선 흐름]

[24시간 서버에서 항상 대기 중]
   │
   ▼
① 스케줄러가 "방송 시간이다" 판단 (예: 매일 저녁, 약간 랜덤)
   │
   ▼
② 방송 시작 전 공지 작성 → 디스코드/카페 게시
   (AI가 매번 다른 문구로 "곧 방송 시작합니다")
   │
   ▼
③ OBS 자동 실행 → 스트림 시작 (트위치/유튜브 등)
   │
   ▼
④ 방송 중 (핵심 루프, 계속 반복)
   - 채팅 읽음 → 다 반응 (기본은 다 읽고 다 반응, 자연스러운 속도)
   - 혼잣말/능동 발화 (채팅 정말 없을 때만)
   - 게임 플레이 (선택)
   - TTS로 말함 → 아바타 입 움직임
   │
   ▼
⑤ 종료 조건 체크 (백그라운드)
   - 최대 시간 도달? / (선택)채팅 저조? / 정해진 종료 시각?
   │
   ▼
⑥ 자연스러운 마무리 멘트 → OBS 스트림 종료
   │
   ▼
⑦ 방송 종료 공지 (선택) → 다음 방송 예고
   │
   ▼
[다시 24시간 대기로]

→ ④(방송 루프)만 기존 오픈소스가 해줌.
  ①②③⑤⑥⑦은 직접 만드는 자동화 레이어.


[2-3. 부품별 역할 정리표]

[2-4. 서버는 어디에 두나]
24시간 켜두려면 둘 중 하나:

- 클라우드 VPS (AWS/가비아 등)
  장점: 안정적, 전기·소음 걱정 없음
  단점: GPU 인스턴스 비쌈 (24시간이면 월 수십만 원 가능)

- 집에 있는 PC
  장점: 초기비용 X, GPU 이미 있으면 유리
  단점: 전기세·소음·인터넷 안정성·정전 리스크

※ 아바타 렌더링·음성 합성이 GPU를 먹어서, 현실적으로 GPU 달린
   집 PC를 서버로 쓰는 경우가 많음. (구체 비용은 8부)

================================================================
3부. AI 페르소나 설계 — 캐릭터를 잡되, 행동은 운영자가 조정
================================================================

이 파트는 "이 방송인이 누구인가(캐릭터)"를 잡는 곳이다.
중요: 캐릭터(말투·성격·배경)는 정하되, "이렇게 행동해라(딜레이 넣어라,
채팅 일부만 답해라)" 같은 행동 규칙은 미리 강제하지 않는다. 그건
운영자가 방송 보고 판단해서 그때그때 지시한다.


[3-1. 페르소나의 뼈대 — "이 방송인은 누구인가"]
LLM한테 "사람처럼 말해"라고만 하면 막연하다. 구체적인 한 사람을
정의해주면 캐릭터가 또렷해진다. 정할 것:

- 이름·나이대·성별 (목소리·말투 기준)
- 성격 (밝음/시니컬/차분 등 — 한 단어 말고 3~4개 형용사)
- 말버릇 (자주 쓰는 단어, 추임새, 어미 — 예: "~거든", "ㄹㅇ")
- 좋아하는 것 / 싫어하는 것 (반응 일관성)
- 금기 (절대 안 하는 말, 안 다루는 주제)
- 배경 설정 (어디 살고, 뭐 하다가 방송하는지)
- 방송 콘셉트 (수다형/게임형/노래형/사연읽기 등)

→ 이걸 '시스템 프롬프트'로 LLM에 넣음. 캐릭터의 토대.

※ 단, 이것도 처음부터 완벽할 필요 없다. 초안만 잡고 방송 돌리면서
   운영자가 "말투 이렇게 바꿔" 하면 고치면 된다.


[3-2. 기본 행동 방침 — 강제 규칙이 아니라 디폴트]
(※ 이전 버전의 "AI티 지우는 7가지 기법"은 삭제. 그건 AI가 추측한
   행동 규칙이었고, 잘못된 접근이었다. 아래는 강제가 아니라 출발점이다.)

기본값(디폴트)은 단순하게:
- 채팅: 기본적으로 다 읽고 다 반응. 사람 없는 1인 시청도 채팅 하나가
  소중하다. 다 반응해주는 게 좋은 방송이다.
- 속도: 자연스러운 속도로 응답. 인위적 딜레이를 기본으로 넣지 않는다.
  맥락상 빠른 반응("ㅋㅋㅋ"에 바로 받아치기 등)이 맞으면 빠르게.
- 말투: 페르소나(3-1)대로. "말 흐려라" 같은 연기 지시를 디폴트로
  강제하지 않는다.
- 자발적 발화: 채팅이 정말 없을 때 가만히 멈춰있지 않게 혼잣말은
  할 수 있게 (이건 대부분 오픈소스 기본 지원). 단 이것도 운영자가
  "너무 많이 떠든다" 하면 줄인다.

→ 이 디폴트에서 시작해서, 운영자가 방송 보고 "이건 이렇게 바꿔"라고
  하면 그때 조정한다. 무엇이 자연스러운지는 운영자가 정한다.


[3-3. 캐릭터에 살 붙이기 (선택)]
캐릭터를 더 또렷하게 하고 싶을 때 쓰는 보조 수단. 필수 아님:

- 대사 예시집: 이 캐릭터가 할 법한 말을 미리 써서 LLM 참고로 줌.
  "이 상황엔 이런 식으로 반응"의 샘플. 캐릭터가 또렷해짐.
- 상황별 반응 방향: 악플/슈퍼챗/모르는 질문 등에 어떻게 반응할지
  방향만 잡아둠. (세세한 강제 아님)

※ "이런 표현 금지" 같은 리스트도 운영자가 실제로 보고 거슬리는 게
   나오면 그때 추가한다. 미리 AI가 정하지 않는다.


[3-4. 목소리]
말이 자연스러워도 목소리가 어색하면 깬다. 그래서 음성이 중요.

- 음성 클로닝: GPT-SoVITS(한국어 지원)로 목소리 학습. 본인 목소리,
  섭외 음성, 라이선스 확보 음성만 안전.
- 감정 실린 TTS: 단조 낭독보다 감정 표현 되는 엔진. GPT-SoVITS는
  감정 표현 풍부한 편.
- 2차 변조: 학습 목소리를 RVC로 한번 더 변환해 톤 미세조정.

[법적 주의] 실존 인물(연예인·지인) 목소리 무단 클로닝은 법적 문제
가능. 본인 목소리거나 동의·라이선스 받은 음성만 안전. 기획 단계에서
반드시 정하고 갈 것.


[3-5. 핵심 마인드셋 — 운영자가 핸들을 쥔다]
가장 중요한 것. 페르소나도 행동도 처음에 완벽하게 못 만든다.
그리고 그걸 완벽하게 만들려고 AI가 추측으로 규칙을 박으면 안 된다.

올바른 방식:
- 캐릭터 초안 + 단순한 기본 행동으로 시작
- 운영자가 방송을 보고 "이 부분이 이상하다/이렇게 바꿔"라고 지시
- 그 지시대로 수정
- 반복

→ "무엇이 사람 같고 무엇이 이상한가"의 판단 주체는 항상 운영자다.
   AI나 개발자가 미리 정의해서 가두지 않는다. 운영자가 보고 이상하면
   알려주고, 그때 고친다. 이게 이 프로젝트의 작업 원칙이다.

================================================================
4부. 방송 자동화 로직 — 시작 / 진행 / 종료 판단
================================================================

맨 처음 물어본 "방송 종료각을 알아서 잡는다"가 여기 핵심. 사람이
감으로 하는 판단을 AI가 하게 만드는 부분이라 설계가 제일 중요.


[4-1. 방송 시작 자동화]
스케줄러가 시간 판단해서 켬. 시작 시각은 운영자가 설정. 매번 정확히
같은 시각이 싫으면 폭을 줄 수도 있음(선택):

- 기본 시간대 + 랜덤 변주: "저녁 7~9시 사이 랜덤"으로 매일 다르게.
- 요일별 패턴: 평일/주말 다르게, 가끔 쉬는 날도. 매일 빠짐없으면 비현실.
- 시작 전 워밍업: 켜자마자 떠들지 말고 "어 들어오시네", "잠깐 세팅 좀"
  같은 자연스러운 오프닝.

기술: cron이 정해진 시각 → OBS WebSocket "스트림 시작" → AI 코어 가동.
이 부분은 코드로 충분히 됨.


[4-2. 방송 진행 — 핵심 루프]
방송 켜진 동안 계속 도는 메인 루프. 매 순간 반복 판단:

[방송 중 루프 - 몇 초마다 반복]
1. 지금 채팅 들어왔나?
   YES → 반응 (기본은 다 반응, 자연스러운 속도로. 인위적 딜레이/선별
          없음. 맥락상 빠른 반응이 맞으면 빠르게.)
   NO  → 다음
2. 채팅 X초 이상 없었나? (조용한가)
   YES → 혼잣말/화제 던지기 (멈춰있지 않게. 단 과하면 운영자가 줄임)
   NO  → 다음
3. 게임 중인가?
   YES → 게임 상황 인식 → 반응 ("어 죽었다" 등)
   NO  → 다음
4. (선택) 컨디션 상태 반영 — 운영자가 원할 때만. 디폴트 아님.
5. 종료 조건 체크 → (다음 섹션)
→ 다시 1번

핵심은 "우선순위". 동시에 여러 개 겹칠 때 뭘 먼저 할지는 정해야 매끄럽다.
다만 채팅을 일부러 빼먹거나 늦추는 게 아니라, 다 반응하되 동시 처리
순서만 정리하는 것이다.

※ 채팅이 못 따라갈 만큼 폭주하는 상황의 처리는, 실제로 그런 상황이
   생긴 뒤 운영자 판단으로 추가한다. 미리 "일부만 답하기"를 박지 않는다.


[4-3. 종료각 판단 — 진짜 핵심]
"알아서 잡는다"의 실체: AI가 진짜 분위기 읽는 게 아니라, "종료할 만한
상황"을 조건으로 정의해주는 것. 조건 여러 개 조합한다.

종료 트리거 후보 (조합, 값은 운영자가 설정):
- 최대 방송 시간: "약 3시간 넘으면 마무리" — 가장 기본.
- 최소 방송 시간 보장: "최소 1시간" — 켜자마자 끄면 이상.
- 채팅 저조 지속: "오래 반응 없으면 종료 고려" — 단, 이 조건을 쓸지
  말지도 운영자 선택. 채팅 없어도 계속 방송하길 원하면 빼면 됨.
- 정해진 종료 시각대: "특정 시각 넘으면 마무리 모드".
- 자연스러운 종료 단계: 뚝 끄지 말고 "오늘 이만 할까" 예고 →
  마무리 인사 → 종료.

랜덤 변주(선택): 종료 시각을 정확히 같게 안 하고 싶으면 폭을 줄 수 있음
(예: 2시간40분~3시간20분 사이). 이걸 원하는지도 운영자가 정함.

[현실적 한계 인정] 이건 AI가 감으로 끄는 게 아니라 설정한 규칙대로
끄는 것. 어떤 규칙이 좋은지(랜덤을 줄지, 채팅 저조로 끌지 등)는 운영자가
방송 보면서 정한다.


[4-4. 종료 후 처리]
방송 꺼지면:
- OBS 스트림 종료 (WebSocket)
- 종료 공지 게시(선택): "오늘 방송 끝! 다음엔 O요일에" AI가 매번 다른 문구
- 이번 방송 로그 저장: 무슨 일 있었는지(슈퍼챗·게임 등) 장기기억에 저장
  → 다음 방송에서 "저번에~" 가능하게
- 다음 방송 시각 계산 → 대기 모드


[4-5. 게임 플레이는 별도 난이도]
"게임도 한다"는 솔직히 가장 어려운 영역:

- 마인크래프트·팩토리오: AIRI가 이미 함. 봇 API로 조작 가능한 게임이라
  상대적으로 가능.
- 그 외 일반 게임: 화면 보고(이미지 인식) 마우스·키보드 조작해야 함.
  게임마다 거의 새로 만들어야 하고 난이도 매우 높음. AI가 사람처럼
  게임 잘하는 건 또 다른 차원.

[현실적 조언] 초반엔 게임 없이 수다·채팅 소통 중심으로 시작. 게임은
마인크래프트처럼 봇 연동 쉬운 것부터. 처음부터 "롤 하는 AI" 노리면
프로젝트 산으로 감.

================================================================
5부. 공지 자동화 — 디스코드 · 카페 등
================================================================

방송 시작/종료 때 "사람처럼" 공지를 자동으로 올리는 부분. 카페도
공식 API로 가능. 플랫폼별 방법·안전도가 다름.


[5-1. 디스코드 — 가장 안전하고 쉬움]
공식 봇 API가 열려 있어 합법·안정적. 자동 공지에 가장 적합.

- 방법: 개발자 포털에서 봇 생성 → 토큰 발급 → 서버 채널 초대 →
  코드로 메시지 전송
- 가능: 특정 채널 공지, 역할 멘션(@everyone 등), 임베드(카드형),
  이미지 첨부
- 난이도: 낮음. discord.py로 몇십 줄
- 안전도: 매우 안전. 디스코드가 권장하는 정상 사용

→ 시작 시 "방송 시작! → [링크]" 자동 게시, 종료 시 "오늘 끝!" 깔끔.


[5-2. 네이버 카페 — 두 가지 경로]

경로 A: 공식 오픈 API (권장)
- 네이버 개발자 센터 앱 등록 → 카페 글쓰기 API
- access token 받아 정상 글 작성
- 안전: 약관 위반 아님. 본인 운영 카페면 더 안전
- 제약: OAuth 인증 절차, API 지원 범위·형식 제한 가능, 토큰 갱신 관리

경로 B: 셀레늄 자동화 (보조)
- 공식 API로 안 되는 부분(에디터 기능, 이미지 다중첨부 등) 브라우저 조작
- 실제 작동 오픈소스 존재 (예약시간·헤드리스 지원도)
- 리스크: 자동화 탐지 가능. 패턴 사람처럼 흩뿌려야. 무리 시 계정 제한
- 권장: 본인 카페 + 빈도 낮게 + 자연스러운 패턴만

현실적 선택: 공식 API 1순위, 안 되는 것만 셀레늄 보완. 빈도 낮게
(방송당 1회 정도) 유지하면 리스크 크게 감소.


[5-3. 공지를 단조롭지 않게 작성하는 법]
같은 템플릿이 매번 똑같이 반복되면 단조롭다. 이건 운영자가 봐도
거슬릴 가능성이 높은 부분이라 기본적으로 변주를 주는 게 좋음
(단, 이것도 운영자가 원하는 스타일대로 조정):

- 매번 다른 문구: 같은 템플릿이 매일 똑같이 반복되면 단조로움. LLM이
  매번 작성하되 페르소나 말투 유지. "오늘 8시 방송이요!" / "심심한데
  방송이나 켤까~" / "ㅎㅇ 오늘도 달려봅시다" 식으로 변주(스타일은 조정 가능).
- 시간 변주(선택): 매번 같은 시각이 싫으면 시작 10~40분 전 사이 랜덤 등.
- 길이·형식 변주: 어떤 날 한 줄, 어떤 날 길게. 이모지 쓰는 날/안 쓰는 날.
- 맥락 반영: "어제 그 게임 이어서", "오랜만에 노래방송" 그날그날 다르게.
  장기기억 연동하면 자연스러움.
- 새벽 게시 회피: 사람은 잘 시간엔 글 안 씀. 비정상 시간대 게시는
  눈에 띄게 어색하니 기본적으로 피하는 게 좋음 (운영자 판단).


[5-4. 다른 플랫폼 (트위터/X, 카카오 등)]
"다른 곳" 일반론:

- 트위터/X: 공식 API 있지만 유료화·정책 변동 잦음. 자동 게시 정책
  그때그때 확인.
- 카카오(오픈채팅 등): 자동화 지원 제한적. 공식 API 범위 확인.
- 공통 원칙: 플랫폼마다 ①공식 API 있는지 ②자동 게시 허용하는지
  ③봇 탐지 빡센지 각각 확인. 한 곳서 되는 게 다른 곳서 막힐 수 있음.

→ 플랫폼 확정하면 그때 각각 정확히 찾는 게 맞음. 지금은 "디스코드
   확실히 안전, 카페 공식 API로 가능, 나머지 확정 시 개별 확인"으로.


[5-5. 공지 자동화 구조 요약]

방송 시작 트리거
   │
   ▼
LLM이 공지 문구 생성 (페르소나 말투 + 그날 맥락 + 랜덤 변주)
   │
   ├─→ 디스코드 봇 API → 채널 게시 (안전)
   ├─→ 네이버 카페 공식 API → 글 작성 (안전)
   └─→ (필요시) 셀레늄 → 카페 보완 게시 (조심)
   │
   ▼
게시 완료 로그 저장

================================================================
6부. 기술 스택과 오픈소스 선택
================================================================

오픈소스 목록 중 이 프로젝트에 실제로 뭘 고를지 정리. 부품별 추천+이유.


[6-1. 두뇌 (LLM)]
비용·품질 트레이드오프 두 갈래:

- 클라우드 API (OpenAI/Claude/Gemini): 품질 최상, 자연스러움 좋음.
  단점: 24시간 돌리면 토큰 비용 누적. 방송 내내 호출.
- 로컬 LLM (Ollama로 오픈모델): 세팅 후 비용 0(전기세 제외).
  단점: GPU 필요, 품질이 클라우드보다 떨어질 수 있음. 한국어는 모델
  선택 중요.

추천: 초반 클라우드 API로 품질 확인+페르소나 잡고, 비용 부담되면 로컬
전환 검토. 한국어 자연스러움이 생명이라 처음엔 품질 좋은 클라우드.


[6-2. 방송 코어 — 베이스 오픈소스]
가장 중요한 선택. → Open-LLM-VTuber 베이스 추천. 이유:

- 채팅 연동/TTS/Live2D/능동발화/장기기억(Letta)/음성 끼어들기 핵심 기능
  이미 다 들어있음
- LLM·TTS·아바타 자유 교체 (한국어 TTS 붙이기 좋음)
- 라이브 스트리밍 연동 구조 이미 있음 (커스텀 가능)
- 윈도우/맥/리눅스 다 됨, MIT 라이선스

대안:
- AITuberKit — YouTube 중심이면. 단 v2부터 상업 라이선스 주의.
- AIRI — 게임(마인크래프트 등) 진지하게 할 거면.
- kimjammer/Neuro — 트위치 중심 + 로컬 모델 위주면.

→ 하나를 베이스로 잡고 없는 기능(스케줄러·종료판단·공지봇) 추가.
   처음부터 새로 짜는 게 아니라 기존 걸 개조하는 것.


[6-3. 입 (TTS)]
- GPT-SoVITS 강력 추천. 한국어 공식 지원, 1분 클로닝, 감정 표현 풍부,
  MIT. 방송 코어에 붙이기 좋음.
- 톤 더 다듬으려면 RVC 2차 변환 추가.


[6-4. 얼굴 (아바타)]
- Live2D + VTube Studio 조합이 표준. 2D, 자료 많음.
- 모델은 직접 제작(어려움)/의뢰/구매.
- 3D 원하면 VRM (AITuberKit 지원).


[6-5. 손발·심장 — 직접 만들 부분]
기존 오픈소스에 없어 새로 코딩할 핵심:

- OBS 제어: obs-websocket으로 스트림 시작/종료, 씬 전환
- 스케줄러: cron/파이썬으로 방송 시간 관리 + 랜덤 변주
- 종료 판단 로직: 4부 룰들을 코드로
- 공지 봇: discord.py + 네이버 카페 API 연동
- 전체 오케스트레이터: 부품들 묶어 지휘하는 메인 컨트롤러

→ 이 부분이 진짜 개발 작업량. 코딩 거의 못하면 여기가 외주 핵심 범위.


[6-6. 보조 인프라]
- 장기기억: Letta 또는 ChromaDB(벡터DB)
- 서버 운영: 자동 재시작 설정(죽으면 자동 재가동), 로그 관리
- 가상 오디오 케이블: TTS 음성을 OBS로 보내는 통로 (VB-CABLE 등)


[6-7. 전체 스택 한눈에]

역할        | 추천 도구                  | 비고
------------|----------------------------|------------------
두뇌        | 클라우드 API → 추후 로컬   | 한국어 품질 우선
방송 코어   | Open-LLM-VTuber            | 베이스, MIT
입          | GPT-SoVITS (+RVC)          | 한국어 클로닝
얼굴        | Live2D + VTube Studio      | 2D 표준
OBS 제어    | obs-websocket              | 직접 코딩
스케줄러    | cron/파이썬                | 직접 코딩
종료 판단   | 자체 룰                    | 직접 코딩
공지        | discord.py + 네이버 API    | 직접 코딩
기억        | Letta/ChromaDB             | 설정
서버        | GPU PC 또는 클라우드       | 8부 참고

핵심: 오픈소스(Open-LLM-VTuber + GPT-SoVITS + Live2D)가 "방송하는
부분"의 70%를 해결, 나머지 30%(스케줄·종료·공지·통합)를 직접 만들거나
외주. 0에서 시작하는 게 아님.

7부. 단계별 구축 로드맵
================================================================

코딩 거의 못하면 이게 제일 중요. 통째로 다 만들려 하면 100% 망함.
작게 쪼개서 각 단계가 "눈에 보이는 결과"를 내도록. 한 단계씩 완성 후 진행.


[7-0. 큰 원칙]
- 한 번에 하나씩. 전체를 한방에 만들려 하지 말고 부품 하나씩.
- 각 단계마다 "되는 걸" 확인. 안 되면 다음으로 안 넘어감.
- 수동 → 반자동 → 완전자동 순서. 처음엔 사람이 버튼, 점점 자동화 비율 ↑.


[7-1. 0단계 — 준비 (결정 사항)]
코딩 전 정해야 할 것. 안 정해지면 뒤가 흔들림:
- 방송 플랫폼 확정 (트위치/유튜브/치지직)
- 방송인 콘셉트 확정 (수다형/게임형 등)
- 페르소나 초안 작성 (3부 — 이름·성격·말투)
- 목소리 확보 방법 (본인/섭외/라이선스)
- 서버 결정 (집 GPU PC/클라우드)
- 직접 할지 외주 줄지 결정


[7-2. 1단계 — 오픈소스 그냥 돌려보기 (수동)]
목표: Open-LLM-VTuber를 내 PC에서 일단 켜본다.
- 설치, 기본 예제로 AI 대화되는지 확인
- 아직 방송 아님. "AI가 말하고 아바타 움직이는지"만
- 막히면 → 설치 가이드 따라하기 또는 외주
→ 되면 "두뇌+입+얼굴" 작동. 제일 큰 산 넘은 셈.


[7-3. 2단계 — 한국어 목소리 입히기]
목표: 원하는 목소리로 한국어를 말하게.
- GPT-SoVITS로 목소리 학습 (1분 음성)
- 오픈소스에 연결해 그 목소리로 말하게
- 페르소나 초안을 시스템 프롬프트로 넣고 말투 확인
→ "내 캐릭터가 내 목소리 톤으로 한국어로 말하는" 상태. 꽤 그럴듯.


[7-4. 3단계 — 채팅 소통 + 방송 송출 (수동 시작)]  ★핵심 검증★
목표: 사람이 켜면 AI가 채팅에 반응하며 방송된다.
- OBS 세팅, 아바타 화면 송출, TTS 음성을 OBS로
- 플랫폼 채팅 연동 → AI가 채팅 읽고 반응
- 아직 시작은 사람이 수동으로 켬
- 실제 짧게 테스트 방송 (비공개로)
→ "AI가 시청자랑 소통하며 방송되는가" 첫 확인. 운영자가 보고
   이상한 부분을 발견 → 그때그때 지시해서 수정 시작 (3부 방식).


[7-5. 4단계 — 종료 자동화]
목표: 켜는 건 수동, 끄는 건 AI가 알아서.
- 4부 종료 룰 구현 (최대시간 기본 + 채팅저조·랜덤변주는 선택, 운영자가 켬)
- 자연스러운 마무리 멘트 → OBS 자동 종료
- 시작보다 종료 먼저 자동화: 테스트가 더 안전 (잘못 켜지는 것보다
  잘못 꺼지는 게 덜 위험)


[7-6. 5단계 — 시작 자동화 (스케줄러)]  ★방송 완전 자동 달성★
목표: 정해진 시간에 AI가 스스로 켠다.
- 스케줄러로 방송 시간 관리 (시작 시각은 운영자 설정, 랜덤 변주는 선택)
- 시작→진행→종료가 사람 없이 한 사이클 도는지 확인
→ "방송 자체는 완전 자동" 달성.


[7-7. 6단계 — 공지 자동화]
목표: 방송 켤 때 디스코드/카페에 공지 자동 게시.
- 디스코드 봇부터 (제일 안전·쉬움)
- 그 다음 네이버 카페 공식 API
- 공지 문구를 AI가 매번 다르게 (5부)


[7-8. 7단계 — 24시간 서버화 + 안정화]  ★유지보수 모드 진입★
목표: 서버에 올려두고 며칠씩 알아서 돌게.
- 서버 배포, 자동 재시작 설정 (죽으면 다시 켜짐)
- 며칠 돌리며 터지는 부분 잡기
- 로그 보며 이상 행동·사고 발언 점검
→ 이때부터 운영자 "유지보수만" 모드.


[7-9. 8단계 (선택) — 게임 붙이기]
목표: 수다 방송 안정되면 게임 추가.
- 마인크래프트처럼 봇 연동 쉬운 것부터
- 안정화 다 된 후의 확장. 처음부터 넣을 게 아님.


[7-10. 로드맵 요약]

0단계: 결정 (플랫폼·콘셉트·페르소나·목소리·서버·직접vs외주)
1단계: 오픈소스 켜보기 (AI 대화 확인)
2단계: 한국어 목소리 입히기
3단계: 채팅소통+방송송출 (수동 켬, 테스트)  ← 핵심 검증
4단계: 종료 자동화
5단계: 시작 자동화 (스케줄러)  ← 방송 완전 자동 달성
6단계: 공지 자동화 (디스코드→카페)
7단계: 24시간 서버화+안정화  ← 유지보수 모드 진입
8단계(선택): 게임 붙이기

중요: 1~3단계만 가도 "AI 방송인이 소통하며 방송하는" 핵심 완성.
4단계부터 "자동화", 7단계가 "무인 운영". 한방에 8단계 노리지 말고
단계마다 결과 확인하며 가는 게 성공의 유일한 길.

================================================================
8부. 비용 · 리스크 · 운영 현실
================================================================

마지막이자 제일 솔직해야 하는 부분. "가능하다"고 많이 말했지만 돈·
리스크·한계를 정확히 알아야 후회 안 함. 환상 깨는 게 목적.


[8-1. 돈은 얼마나 드나]
정확한 금액은 선택에 따라 크게 달라 단정 못 함. 어디서 돈 나가는지 항목:

초기 비용 (한 번):
- GPU PC (없으면) — 음성·아바타에 GPU 필요. 가장 큰 초기 비용 가능
- Live2D 모델 — 직접 제작(시간)/의뢰(비용)/구매(비용)
- 목소리 — 본인이면 0, 성우 섭외면 비용
- 외주 개발비 (직접 안 하면) — 작업량에 따라 천차만별

운영 비용 (매달):
- LLM API 비용 — 24시간 클라우드면 누적. 로컬 전환하면 0
- 전기세 — 집 GPU PC 24시간이면 무시 못 함
- 클라우드 서버비 — 클라우드 쓰면. GPU 인스턴스 비쌈
- TTS API — 로컬(GPT-SoVITS)이면 0, 클라우드면 비용

비용 절감 핵심: LLM·TTS를 로컬로 돌리면 매달 비용 크게 감소. 대신 GPU
초기 비용·전기세 감수. "클라우드 다 쓰기"는 편하지만 24시간이라 돈이 샘.


[8-2. 기술적 리스크 (막힐 수 있는 곳)]
- 한국어 자연스러움: 처음엔 어색할 수 있고, 운영자 피드백으로 다듬는
  과정이 필요. 한 번에 완성 안 됨.
- 음성 품질: 클로닝 목소리가 감정·억양에서 어색할 수 있음. 완벽은 아직.
- 게임 플레이: 마인크래프트 외 일반 게임 매우 어려움. 처음부터 노리면 좌초.
- 장시간 안정성: 24시간이면 메모리 누수·프로세스 죽음·API 끊김 등 별별 일.
- 돌발 발언: AI가 부적절/이상한 말 가능. 필터링·페르소나 보강 필요. 라이브라
  한번 나가면 주워담기 어려움.


[8-3. 플랫폼·법적 리스크]
- 방송 플랫폼 약관: 트위치/유튜브/치지직이 AI 자동 방송을 어떻게 보는지
  확인 필요. 무인 방송 정책 플랫폼마다 다르고 바뀔 수 있음.
- 카페 자동 게시: 5부 정리. 공식 API 안전, 셀레늄 조심. 본인 카페·저빈도면
  리스크 낮음.
- 음성 저작권: 실존 인물 무단 클로닝 = 법적 문제. 본인/동의/라이선스만.
- 수익화: 슈퍼챗·광고로 수익 낼 경우 플랫폼 수익화 정책·AI 콘텐츠 규정 확인.


[8-4. "완전 무인"은 환상이라는 것]
가장 정직하게. "사람은 유지보수만"의 그 유지보수가 0이 될 순 없음:

- 초반 몇 달: 손 많이 감. 페르소나 튜닝, 버그 잡기, 운영자 피드백 반영.
  "유지보수"가 아니라 거의 "공동 운영" 수준.
- 안정화 후: 그제서야 하루 5~10분 점검으로 감소. 로그 보고 사고 확인·조정.
- 완전 방치는 위험: AI가 며칠 아무도 안 보는 채 돌면 언젠가 사고. 최소
  모니터링은 계속 필요.

현실적 기대치: "버튼 하나로 영원히 굴러가는 무인 방송국"이 아니라
"초반 공들여 키운 뒤 저관리로 운영하는 반자율 방송인". 이 기대치로
시작하면 실망 안 함.


[8-5. 직접 할까, 외주 줄까 — 판단 기준]

직접 한다면:
- 장점: 비용 절감, 내가 이해해 유지보수 쉬움, 자유 수정
- 단점: 파이썬 기초·터미널·서버 배워야. 시간 오래. 막히면 멘붕
- 적합: 시간 있고 배울 의지 있고 천천히 가도 되는 경우

외주 준다면:
- 장점: 빠름, 막힘 없음, 전문가가 만듦
- 단점: 비용, 요구사항 명확 전달 필요(이 기획안이 그 역할), 유지보수도
  계속 맡기거나 인수인계 필요
- 적합: 빨리 결과 원하고 예산 있고 코딩 배울 시간 없는 경우

현실적 절충안: 1~2단계(설치·목소리)는 직접 시도, 막히거나 3단계 이후
복잡한 통합(스케줄러·종료판단·공지봇)은 외주. 이 기획안을 외주
개발자에게 그대로 넘기면 요구사항 문서가 되어 견적·구현 수월.


[8-6. 마지막 정리 — 솔직한 종합 평가]
- 기술적으로 가능한가? → 원한 거 전부 가능. 카페 공지까지.
- 쉬운가? → 아니. 부품 조립 + 직접 개발 + 긴 튜닝의 중급 이상 프로젝트.
- 코딩 못해도 되나? → 직접 하려면 배워야 하고 안 배우면 외주. "떠먹여주면
  복붙만으로 완성"되는 규모 아님.
- 돈이 드나? → 초기(GPU·모델·외주) + 운영(API·전기·서버). 로컬로 절감.
- 완전 무인 되나? → 초반 공들이고 후반 저관리. 완전 방치는 위험.
- 그래서 할 만한가? → 명확한 목표(이 기획안)와 단계별 접근(7부)이 있으면
  충분히 도전할 가치 있음. 단, 한방에 다 하려 말고 작게 시작.

[전체 요약 한 문단]
사람 손 안 쓰고 AI가 자율로 운영되는, 사람처럼 느껴지는 AI 방송인은
기술적으로 전부 구현 가능하다(카페 공지 포함). 기본 방침은 "채팅 다
반응 + 자연스러운 속도"이고, 무엇이 자연스러운지의 판단 주체는 운영자다
(AI가 행동 규칙을 미리 추측해서 박지 않는다 — 3부). 종료는 설정한
규칙대로 끄는 것(4부)이며, Open-LLM-VTuber + GPT-SoVITS + Live2D를
베이스로 70%를 해결하고 스케줄러·종료판단·공지봇을 직접 만들거나 외주
주는 구조(6부)다. 한방에 다 만들지 말고 0~8단계로 쪼개(7부) 한 단계씩
결과를 확인하며 가야 하며, "완전 무인"은 환상이고 초반 공들인 뒤 저관리로
운영하는 반자율이 현실적 목표(8부)다.
