# v65 · 원본 064 중복·누락 여부 확인 — 오프라인 메모리 구조 검사

## 원본 계획과 구현 범위

`docs/ORIGINAL_PLAN.txt`, `docs/ROADMAP_100.md`, `config/roadmap.json`, README, 061~063단계의 코드·테스트·검증 로그를 검토했습니다. 원본은 **모든 채팅에 반응**하고 임의 선별·인위적 지연을 기본으로 넣지 말 것을 요구합니다. 동일한 내용의 채팅은 서로 다른 정상 메시지일 수 있으므로 **내용만 같다고 삭제·차단하지 않습니다**.

이번에는 기존 062 `OfflineChatReceiveBuffer` 및 063 `OfflineChatOrder`를 그대로 읽는 `OfflineChatIntegrity`를 추가했습니다. 네트워크 연결, 별도 수신기, AI 응답, 자동 처리, 파일 저장은 추가하지 않았습니다.

## 사용법

1. 기존 `플랫폼 채팅 연결 모의`에서 수동 가상 연결을 시작합니다.
2. `채팅 수신 모의`에서 테스트 채팅을 수동 접수합니다.
3. 필요한 경우 `메시지 순서 관리`에서 수동 동기화·순서 확인을 수행합니다.
4. `채팅 중복·누락 점검` 탭에서 **중복·누락 수동 점검**을 누르면 **검사 시점**의 수신함과 순서 관리 기록을 읽기 전용으로 검사합니다.

검사 내용:
- 수신함의 로컬 수동 접수 순번 중복·관찰된 범위의 공백·순서 역전·형식 오류
- 062 수신함과 063 동기화 기록의 접두 기록 불일치·잘림·변조
- 수동 동기화 전 메시지 수 별도 표시 (**누락으로 오판하지 않음**)
- 동일 플랫폼·닉네임·내용의 반복 그룹과 추가 건수 (**정상 중복 가능**, 자동 제거 없음)
- 063 확인 처리 건수/대기 건수 및 모의 실패 중단 상태

수신/순서 처리 버튼으로 상태가 변경되면 GUI의 기존 검사 결과를 **만료 표시**하고, 운영자가 다시 버튼을 눌러야 최신 결과를 볼 수 있습니다. 검사는 수신함, 대기열, 설정, 데이터베이스를 수정하지 않습니다.

## 반드시 남겨야 할 검증 경계

- 순번은 프로그램에서 수동 접수한 **로컬 순번**입니다. 플랫폼 서버의 메시지 ID·전송 순번이 아닙니다.
- 실제 플랫폼에서 수신되지 않은 메시지, 마지막 접수 이후의 누락, 서버 재전송, 동일 내용 메시지가 정말 중복 송신된 것인지 **판정 불가**합니다. 빈 수신함에 오류가 없다는 것은 실제 채팅 수신 성공의 증거가 아닙니다.
- 실제 치지직/유튜브/트위치 접속, AI 반응, OBS 송출, Windows 실기기/EXE, 사용자 최종 승인은 미실시입니다.
- 원본 064 로드맵 체크박스와 JSON 상태는 **pending**으로 보존합니다. 코드 개발 도달 범위만 **64/100**으로 보고합니다.
