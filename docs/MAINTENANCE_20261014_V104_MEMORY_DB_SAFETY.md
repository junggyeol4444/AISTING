# AISTING v104 유지보수 — 로컬 대화 기억 SQLite 비파괴 초기화

원본 100단계의 새로운 단계가 아니라, 기존 `LocalMemory` SQLite 안전성 수정이다. Windows 실기기·EXE·실제 AI/음성/아바타/OBS/플랫폼 채팅·장시간 방송·사용자 승인은 이번에 실행하거나 확인하지 않았다.

## 재현된 결함

`src/ai_broadcaster/offline_chat.py`의 이전 `LocalMemory.__init__()`은 경로에 SQLite 파일이 이미 있어도 `CREATE TABLE IF NOT EXISTS history`를 수행했다. 파일이 다른 앱의 SQLite DB이거나, `history` 스키마가 다르거나, 심볼릭 링크를 통해 다른 DB를 가리키는 경우에도 초기화를 거부하지 않았다. 새 회귀 시험 7건을 기존 v103 코드에 적용한 결과 **2건 통과, 5건 실패**했다(`logs/MAINTENANCE_20261014_V104_BASELINE_FAIL.log`). 이는 실사용자 PC에서 발생했다는 주장이 아니라 개발용 임시 DB에서 재현한 결함이다.

## 수정 내용

- 이미 존재하는 파일은 먼저 읽기/쓰기 연결의 **스키마 검사**만 수행하고, 기존 파일에 새 `history` 테이블을 생성하지 않는다.
- `sqlite_master`에서 기존 `history` 단독 테이블인지 확인하고, 레거시 필드의 이름·자료형·NOT NULL·기본키 및 SQLite `application_id=0`을 검증한다. 다른 테이블·뷰·트리거가 있거나 구조가 다른 DB는 오류를 반환하고 변경하지 않는다.
- 링크/정션 경로(대상 파일 및 상위 경로)를 거부한다. 이후 읽기·추가·삭제에서도 경로와 스키마를 재검증한다.
- 신규 DB는 `O_CREAT | O_EXCL`로 독점 생성하고, 생성 중 실패 시 **이번에 만든 파일만** 정리한다.
- 재사용 중 DB 파일이 사라지면 `mode=rw`로 오류를 반환하고 빈 DB를 몰래 새로 만들지 않는다.
- 기존 레거시 `history` 테이블과 저장된 한국어 메시지는 유지하며, 정상 새 DB의 추가·조회·삭제 기능도 유지한다.
- SQLite 연결은 기존과 같이 트랜잭션 종료 후 `close()`한다.

## 검증 범위와 호환성

신규 단위 테스트 12건, 전체 2,014건, Linux Xvfb GUI 스모크 99건, AST 313개, 최종 ZIP 재압축·독립 압축 해제 검증을 수행한다. 실제 결과는 `logs/MAINTENANCE_20261014_V104_*` 및 ZIP 외부 보고서 참조.

기존 대화 기억 DB에 **다른 사용자 정의 테이블·트리거·뷰를 추가해 사용하던 환경**은 이제 비파괴적으로 오류를 반환한다. 데이터 자동 수정·삭제·이전은 하지 않는다. 심볼릭 링크/정션으로 기억 폴더를 구성한 경우도 자동 접근하지 않는다. 이는 무조건적인 기존 배포 환경 호환성을 보장하는 변경이 아니며 Windows 실기기 확인이 필요하다.

같은 스키마를 우연히 가진 외부 DB를 완벽하게 구분할 수는 없다. 다중 프로세스가 파일 경로를 교체하는 극단적인 경쟁 상황, Windows 파일 잠금/정션 동작, 실제 장시간 사용에서의 메모리·연결 안정성은 이번 오프라인 테스트로 입증되지 않는다. 운영자 최종 승인 상태는 `pending`을 유지한다.
