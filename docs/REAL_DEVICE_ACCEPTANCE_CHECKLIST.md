# AISTING 실제 동작 확인 대기 목록 (사용자가 직접 선택·검증)

**현재 상태: 전체 항목 UNVERIFIED / 사용자 확인 대기.** 아래는 나중에 운영자에게 한 번에 전달할 수 있도록 모아 둔 **확인 항목**이며 실행을 완료했다고 주장하지 않는다. 외부 서버/OBS/계정 연결 등 원래 금지된 작업은 명시적 승인 전까지 계속 금지한다. 사용자 PC의 정보·음성 샘플을 자동 수집하거나 원격으로 조작하지 않는다.

## 왜 내부 테스트만으로 보증이 안 되는가

현재 대부분의 모의 테스트는 자체 코드의 예측 가능한 입력·출력만 검사한다. 실제 Windows 오디오 드라이버/음성, 사용자의 설치 환경, OBS와 방송 플랫폼 API, 네트워크 장애와 실시간 경쟁 상태를 재현하지 못한다. 한 기능 수정이 다른 기능을 깨뜨릴 수 있으므로 테스트는 *위험을 줄이는 증거*이지 '실제 제품 완성' 증명이 아니다. 새 회귀 테스트와 매번 전체 테스트가 필요하고, 주요 경계에서는 운영자가 승인된 환경에서 통합 시험해야 한다.

추천 검증 순서는 **① Windows 설치 없는 소스/UI 기동 및 기존 설정 백업 확인 → ② 로컬 대화/가상 화면 → ③ 권리 확인된 음성/실제 아바타 → ④ 명시적 승인 후 플랫폼·OBS 연결 → ⑤ 비공개 시험 방송 → ⑥ 장시간 테스트 및 사용자 최종 승인**이다. 사용자 승인 없이는 ④~⑥을 진행하지 않는다. 이 계획 때문에 기존 오프라인 개발을 중단하지 않는다.

문제가 발생하면 그때 실행한 Windows 버전, 선택한 기능, 화면에 표시된 오류 메시지(비밀번호·계정 키·개인정보 제외)만 운영자가 원하는 범위에서 직접 알려주면 원인을 분석한다. 수집 자동화/원격 접근은 하지 않는다.

## v79 추가 대기 · 실제 방송 시간과 종료 검증

- 개발 환경에서 검증한 것은 **사용자가 직접 입력한 가상 경과 초/분에 대한 판정 로직**뿐이다.
- **Windows/실제 방송 확인 필요:** 실제 시작 시각 보존, 경과 시간(절전/재개 포함), 최소시간 이전 종료 차단, 최대시간 마무리 요청, 방송 화면/음성 종료 동기화, 장애 이후 재진입, 실제 OBS 종료/권한 및 수동 중지 안전성.
- 이 작업은 **실제 송출·Windows PC 접근·정보 자동 수집·OBS 연결에 대한 승인을 의미하지 않는다.** 실기기 검증은 운영자가 별도로 수행하거나 승인해야 한다.

## v80 추가 대기 · 종료 멘트/방송 종료 실동작 검증

- 개발 환경에서 확인: 최대시간 도달 판정 입력 → 예고 문구 표시 → 인사 문구 표시 → **가상 종료 플래그**. 문구 표시 실패/중복 진행 방지/시간·장면 설정 변경 시 무효화.
- **사용자 확인/승인 대기:** 운영자가 실제 원하는 말투·멘트 자연스러움/발음·음성 장치·마지막 채팅 대기열 처리, OBS에서 종료가 안전하게 진행되는지, 강제 종료/재시도/종료 공지 권한, 방송 플랫폼 화면상 실제 종료 및 장시간 타이머/장애 복구.
- **절대 혼동 금지:** `virtual_ended=True`는 실제 송출 종료 확인이 아니다. 실제 OBS·계정·플랫폼 접속은 사용자 승인 이전 금지다.

## v81 추가 대기 · 자동 종료 전체 검증의 실제 사용 증거

- 내부에서 실행한 것은 **수동 입력 시간 + 가상 캐릭터 문구 + 메모리 종료 플래그**의 12개 독립 상태검사뿐이다. 이 결과가 실제 방송 안전 종료를 증명하지 않는다.
- **실제 사용자 검증/승인 대기:** Windows EXE/실시간 타이머·절전/복귀, 실제 TTS 발화/음소거·실제 아바타/OBS 송출과 동기화, 마지막 시청자 채팅 잔여분 처리, 실제 방송 끝났는지 확인, 종료 실패 시 수동 개입, 오디오·영상 지연/권리, 플랫폼 비공개 상태 및 사용자 최종 승인.
- 사용자의 PC 정보·계정·음성 자료를 승인 없이 수집/연결/설치하지 않는다. 이후 코드 변경마다 Linux 모의 테스트를 되풀이하더라도 Windows 실기기 검증을 대체할 수 없다.

## v82 추가 대기 · 방송 시작 일정 초안의 실제 Windows 검증

- 오프라인에서 검증한 것은 수동 입력 날짜·KST 고정 UTC+9 계산, 메모리 일정 목록, 운영자가 직접 요청한 JSON 저장/불러오기/삭제이다. **백그라운드 방송 예약 등록은 없다**.
- **사용자/Windows 검증 대기:** 실제 PC 시간대·시계 오류·절전/재부팅/오프라인 날짜와 다른 환경에서의 표시, 여러 날짜/요일 수정과 저장 데이터 복구, 백업 및 파일 권한, 창 크기/접근성, 기존 사용자 설정 무손상 확인.
- 실제 예정 시각에 AI/OBS/플랫폼 방송 자동 시작/종료가 작동하는지, 일회성 휴무/중복 방송 방지, 공지, 실제 시청·음성·영상 전송 및 계정 권한은 **미구현·미검증**. 사용자 명시적 승인 전 계정 연결/OBS/실방송 금지.

## v83 추가 대기 · 082 자동 방송 시작 제어 실환경 확인

- 내부 시험은 운영자가 입력한 **KST 기준 시각**과 메모리 일정 초안을 비교하여 가상 시작/종료 플래그를 설정하는 *수동 시뮬레이터*만 포함한다. 실제 시계 읽기, 타이머 감시, 운영체제 작업 스케줄러 등록, 사용자 부재 중 실행은 **없다**.
- 운영자 승인 후 실기기에서 별도 확인: Windows 시각/시간대와 절전·재부팅 후 시작 시점 판정, 여러 스케줄이 겹치는 상황, UI 종료 후 중복 처리 방지(현 모델의 중복 기록은 메모리 내에서만 유지), 장시간 스케줄 감시 및 수동 중지/실패 복구.
- **미구현·승인 대기:** 방송 전 공지 권한 및 전송, 실제 OBS 실행/송출, 플랫폼 인증·실제 시청 가능 여부, 실제 음성·아바타·채팅 연동. 테스트에서 `mock_started`가 반환됐더라도 실제 송출 성공이나 계정 승인 상태를 의미하지 않는다.
- 사용자 PC 접근, 설치, 계정·음성 자료 수집, 방송 송출을 이번 테스트 목적으로 실행하지 않았다. 로드맵 082와 010 최종 승인은 `pending` 유지.

## v84 추가 대기 · 원본 083 실시간 시작→종료 통합 시험

- Linux에서 확인한 것은 **고정된 가상 시간 입력과 메모리 시작/종료 상태 연결**만이다. 이 감사 14/14 통과는 실제 방송이 한 번 시작·진행·종료됐다는 뜻이 아니다.
- 운영자가 승인된 Windows 기기에서 직접 확인 필요: 실제 시간대/절전·재시작/이중 시작 방지, 공지 게시 실패·재시도·중복, AI·채팅·음성·아바타·OBS 실제 시작 순서 및 지연, 1~3시간 장시간 안정성, 잔여 채팅 처리, 실제 종료 멘트·음성 및 OBS 종료 확인, 인터넷 오류·권리·시청자 개인정보·사람이 느끼는 자연스러움.
- 사용자 PC 자료/음성/계정 정보 자동 수집, 계정 연결, 실제 방송·OBS 제어는 **별도 명시적 승인까지 금지**. 내부 테스트만으로 실기기 사용 가능 판단 금지.

## v85 추가 대기 · 방송 시작 전 공지 실제 사용 검증

- 개발 환경에서 확인한 것은 선택된 **저장 설정**과 운영자의 수동 KST 날짜/시각·주제를 이용해 로컬 `tk.Text`에 고정 규칙 초안을 표시하는 기능뿐이다. 자연스러운 AI 공지 문구 자동 작성·예약·전송을 검증하지 않았다.
- Windows PC에서 직접 확인: 실제 폰트·한글·화면 크기/붙여넣기 동작, 운영자가 내용을 손으로 검토·수정할 수 있는 별도 워크플로, 본인 말투·운영 스타일 적합성, 날짜/요일/시간대 오입력 방지.
- **별도 명시적 승인 이후에만** 외부 디스코드/카페 계정 연결·공식 API 권한·실제 게시/링크/중복 방지·취소/삭제/오류 복구·이용 약관·개인정보 검증. Windows 실기기/EXE와 사용자 최종 승인 모두 대기.

## v86 추가 대기 · 디스코드 공지 실연동 및 안전성 검증

- 내부에서 검사한 것은 **전송되지 않는 JSON 미리보기 형식**뿐이다. 실제 디스코드 인증/채널 연결/API 호출, 공지 게시와 읽힘, 권한/약관 확인은 검증하지 않았다.
- 사용자 직접 확인/명시적 승인 후 필요한 항목: Windows Tkinter/EXE 한글·화면, 실제 공지 내용/링크 및 채널을 어디로 게시할지, 봇 권한 범위, 인증정보 보관·갱신, 중복 게시·실패·재시도·삭제, 멘션 정책과 다른 이용자 권리/개인정보, Discord API 버전/속도 제한 및 실제 운영 중 장애.
- 본 단계는 사용자에게 계정·토큰·PC 자료를 요청하거나 자동 수집하지 않는다. `send_ready=false`/`published=false`는 실제 발송 성공의 반대 의미다. 원본 085와 최종 승인 010은 대기.

## v87 추가 대기 · 원본 086 방송 시작 공지 자동 게시 실제 작동 검증

- 현재 모의 기능은 수동 입력 KST 시각, 082 **가상 방송 시작** 플래그, 084 검토용 문구, 085 미전송 JSON을 재사용한 Tkinter 화면 출력만 검사한다. Discord로 전송하지 않았고 자동 게시되었다고 주장하지 않는다.
- 운영자 명시적 승인 후 직접 확인해야 할 것: Windows GUI/EXE 한글·폰트·입력, 실제 방송 시작 시각과 공지 송신 시점, 올바른 대상 채널/계정/봇 권한, API 요청/응답과 실제 게시 확인, 공개/비공개 링크·멘션 범위, 재부팅/앱 충돌 후 재게시 방지(현 모의 기록은 메모리뿐), 네트워크 실패·재시도·삭제/정정·권한 만료·Rate limit, 이용약관/개인정보/기타 권리.
- 실제 방송/OBS/채팅/음성/아바타 결합 상태에서 시작 공지가 나가는지와 010 최종 인수 승인은 **별도로 미검증**. 계정 자격증명/사용자 PC 자료를 이번 단계에서 요구하거나 수집하지 않았다.

## v100 (원본 099) 운영자 점검표 및 수동 기록의 실제 확인 대기

- GUI 점검표의 `운영자 확인 입력`은 사람이 입력한 주장이지 Windows/실방송/권리
  확인을 실제 수행한 증거가 **아니다**. 모든 항목을 확인 입력해도 자동으로 승인하지 않는다.
- 사용자가 직접 승인하고 실제 기기·서비스를 검증하기 전까지 Windows/EXE,
  음성·아바타·OBS·방송 플랫폼·실제 비용·콘텐츠 권리·몇 시간/며칠 안정성은 미검증.
- SQLite 연결 미종료 `ResourceWarning`은 지속 미해결이며 실제 DB 연결 수명,
  프로세스 종료, 반복 사용·백업/복구를 정식 점검해야 한다.
- 사용자 기기나 로그를 자동으로 수집하지 않으며, 수동 JSON 기록은 기본 비저장,
  사용자가 명시적으로 경로를 지정할 때만 새 파일 생성. 인증정보를 작성·공유하지 말 것.
- 본 단계는 원본 099의 유지보수 UI 구조만 부분 구현. 원본 100 최종 검수와 010 사용자
  승인 `pending` 상태는 그대로 유지한다. 내부 통과 ≠ 방송 가능한 제품.
