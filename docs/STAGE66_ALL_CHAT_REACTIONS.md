# v66 · 원본 065 모든 채팅에 반응하는 기본 구조 — 오프라인 모의 연결

## 기획안 및 이전 구현 확인

`docs/ORIGINAL_PLAN.txt` 1부의 핵심 원칙은 **모든 채팅에 반응하고 임의 선별·인위적 지연을 기본값으로 두지 않는 것**입니다. `docs/ROADMAP_100.md`, `config/roadmap.json`, README, `docs/STAGE63_OFFLINE_CHAT_RECEIVE.md`, `docs/STAGE64_CHAT_ORDER.md`, `docs/STAGE65_CHAT_INTEGRITY.md`, 테스트/검증 로그를 기준으로 다음 단계만 진행했습니다.

037단계의 `AllChatPolicySession`은 별도 수동 입력 대본을 처리하는 독립 모의 정책 검사였습니다. 065단계에서는 **중복 수신기를 만들지 않고** 062단계 `OfflineChatReceiveBuffer`와 063단계 `OfflineChatOrder`를 **실제로 연결**한 `OfflineChatReactions`를 추가했습니다. 모의 응답은 022/037단계가 사용하는 기존 `MockCoreReplyPort`를 재사용합니다. 063단계의 **순서 확인**은 065단계의 **응답 성공**으로 간주하지 않습니다.

## 화면 사용 순서

1. `플랫폼 채팅 연결 모의`에서 수동 가상 연결을 시작합니다.
2. `채팅 수신 모의`에서 테스트 메시지를 하나씩 접수합니다.
3. `메시지 순서 관리`에서 **수동 동기화**합니다.
4. 새 `전체 채팅 모의 응답` 탭에서 **순서 기록 수동 동기화** 후 `다음 1건 모의 응답` 또는 `최대 50건 수동 처리`를 누릅니다.
5. 실패를 시험하려면 `다음 1건 모의 실패`를 누르고, 대기 순번이 유지되는지 확인한 뒤 `오류 수동 재개`를 누릅니다.

같은 내용, 여러 플랫폼, 다른 발신자라도 접수된 각각의 로컬 순번을 보존합니다. 응답 대기열은 메모리 전용이며 수신/순서 원본 데이터·설정·SQLite를 변경하지 않습니다. 모의 실패나 잘못된 응답이 발생하면 **현재 메시지를 삭제하지 않고 중단**합니다. 자동 재시도, 백그라운드 처리, 타이머/인위적 딜레이는 없습니다. 배치 버튼은 한 번에 최대 50건만 명시적으로 처리합니다.

## 경계 및 승인 상태

- **실제 플랫폼 채팅 수신 0건**, 실제 AI 모델 응답 0건, 실제 TTS/아바타/OBS/방송 없음.
- 모든 **수동 접수된 모의 채팅**에 대한 FIFO 응답 구조만 검사했습니다. 실시간 처리율, 자연스러운 속도, 실제 시청자 반응 품질은 검증하지 않았습니다.
- 066단계 `인위적 응답 지연 없이 반응 테스트`는 별도 다음 단계입니다. 이번에는 인위적 지연 로직을 추가하지 않았다는 구조적 사실만 확인했습니다.
- Windows 10/11 실기기 및 EXE 미검증, 사용자 최종 승인 010 대기. 로드맵 065 체크박스와 JSON `pending`은 변경하지 않습니다. **코드 개발 도달 범위만 65/100**입니다.
